# 设计取舍与故障复盘

这份文档记录**为什么这么做**，而不是做了什么。做了什么看 [README](../README.md)。
每条结论都对应一次真实故障或一次明确的权衡；没有真实依据的"最佳实践"不写进来。

## 1. 为什么把文件操作单独做成模块

三个故障的共同点是：**代码在一个平台通过、在另一个平台失败，且失败方式不是业务错误，
而是操作系统的属性差异。**

### 故障 A：只读属性让 `os.replace` 抛 `EPERM`

归档同步脚本用 `os.replace(tmp, target)` 覆盖目标文件。在 macOS/Linux 上一切正常；
在 Windows 上部分目标文件带只读属性（`.git` 对象文件、从 zip 解压出的文件常见），于是：

```
PermissionError: [WinError 5] 拒绝访问。
```

更麻烦的是它只影响**一部分**文件，静默地跑完整个同步后，才在比对阶段发现 84 个文件
里有 9 个没更新、1 个内容不一致。POSIX 没有只读属性这一层，所以这段代码在 POSIX 上
永远测不出问题。

**取舍**：

- `atomic_replace()` 在替换前先 `clear_readonly(dst)`，遇 `PermissionError` 再清一次并
  重试（默认 3 次，间隔 0.05s）。重试是为了覆盖杀毒软件或索引服务瞬时占用。
- 重试耗尽时抛**最后一次的原始 `PermissionError`**，而不是包装成新异常。理由：调用方
  和日志系统依赖 errno 判断"权限"还是"占用"，包装会丢掉这个信号。
- `clear_readonly()` 返回布尔值而不是静默执行，调用方可以记录"这次动了哪个文件的属性"。

### 故障 B：中文路径下 Python 控制台直接崩溃

同一份脚本，输出中文日志到控制台时进程以 `0xC0000005`（访问冲突）退出，没有任何
traceback。这不是可捕获的异常，因此 `try/except` 完全无效。

**取舍**：

- 本仓库自身的测试与工具脚本**只向控制台写 ASCII 状态行**，完整信息写 UTF-8 文件。
  `tests` 里保留了中文与 emoji 文件名的用例（`test_chinese_names_survive`），因为
  **数据**必须支持 Unicode——只是**控制台输出**要规避。
- 这个约束写进 README，而不是留给下一个人再踩一次。

### 故障 C：大小写与 Unicode 折叠造成重名

批量导出的文件在 macOS 上相互覆盖（默认大小写不敏感），在 Windows 上直接报"文件已存在"，
而 Linux 上风平浪静。同类问题的第二种形态是 NFC/NFD：视觉完全相同的 `café.md` 可能是
两个不同的字节序列。

**取舍**：

- `find_collisions()` 默认按 `casefold()` + NFC 折叠分组，返回**分组**而不是"第一个冲突"，
  因为调用方往往需要整组改名或整体拒绝。
- `casefold()` 而不是 `lower()`：`STRASSE` 与 `straße` 应当被视为同名。
- 默认值站在"会覆盖别人文件"的一侧——宁可多报，不可漏报；需要精确比较时显式传
  `case_sensitive=True`。

## 2. 为什么 `safe_join` 不做符号链接检查

`safe_join()` 只做字面量层面的规范化与包含判断：拒绝 `..` 逃逸、绝对路径片段、
盘符相对形式、UNC 与 NUL。它**不**调用 `realpath`，因为：

1. 检查时与使用时之间存在竞态（TOCTOU），即便 realpath 通过，写入前目录仍可能被换成链接；
2. 解析链接需要访问文件系统，会让这个纯函数变成有 I/O 依赖、难以单测的东西；
3. 真正防链接逃逸的可靠做法是"打开时校验"（`os.open` + `O_NOFOLLOW`，Windows 用
   `FILE_FLAG_OPEN_REPARSE_POINT`），那属于上层策略。

因此文档明确写出这个边界，而不是给出"看起来安全"的假象。

## 3. 为什么 `check_path_length` 用严格小于

Windows 文档的 260 是**含结尾 `\0` 的缓冲长度**，可用字符是 259。用 `length < limit`
表达"可用预算"，比 `length <= 260` 少一次边界争议，也让 `limit` 参数的语义在任何平台上
一致（自定义 `limit=200` 时就是 200 个字符以内）。

## 4. 为什么零依赖、为什么还要支持 3.9

- 零依赖：这个库会在别人的构建脚本、CI、一次性迁移脚本里被调用。每引入一个依赖，
  就多一次"我的环境装不上"的失败机会。
- 3.9：它是许多企业镜像与教学环境的基线。代价是不能用 `match`、`X | Y` 运行时语法，
  因此全部模块使用 `from __future__ import annotations` + `Optional[...]` 写法。

## 5. 为什么 CI 必须跑 Windows

本项目的核心价值是"消掉平台差异"，只在 Linux 上跑 CI 等于没测到要害。矩阵因此是
`{ubuntu, windows} × {3.9, 3.12}`：低版本保证语法兼容，高版本保证未来兼容，两个平台
保证不出现"只在某个平台成立"的假设。

## 6. 已知限制

- `atomic_replace()` 只处理单文件；整目录替换需要调用方自行保证顺序。
- 未处理 Windows 的 8.3 短名（`PROGRA~1`）与 NTFS 备用数据流（`file.txt:stream`）。
- `sanitize_filename()` 不处理 RTL 覆写字符等"视觉欺骗"类 Unicode（如 `U+202E`）；
  需要防伪装文件名时应在展示层过滤。
- `find_collisions()` 不做目录树的递归遍历，只对传入的名字列表负责。

## 7. 下一步的优先级依据

先做"能防止数据被覆盖"的功能（`scan` 子命令、目录树重名检查），再做便利性功能。
理由：这个库的定位是**守门**，不是脚手架；漏报的代价远高于少一个便捷参数。
